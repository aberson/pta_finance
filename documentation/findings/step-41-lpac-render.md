# Step 41 findings: LPAC render spike

Verdict: **pass**

A real render inside the attested LPAC worker of a PDF whose only font is the non-embedded
standard Type1 `/Helvetica` produces legible glyphs. Its pixels are byte-identical to the same
render outside the LPAC. It clears both calibrated thresholds. No blocked findings file
exists, so Step 42's condition
(`test -s documentation/findings/step-41-lpac-render-blocked.md`) is false. Steps 43 and 44
keep the LPAC worker as the PDF boundary (§ 6.3 of the receipt-autofill plan).

## What was measured

- **Production path.** `bank_statements._render_native_page_in_worker` sends an
  `operation` = 2 request through the same `native_sandbox.start_native_pdf_worker` launch
  and attestation that statement extraction uses. It uses the closed five-file staged
  allowlist and the existing worker ceilings. The worker answers with the § 5A `rendered`
  frame: one page of raw gray8 pixels, zlib-compressed and base64-encoded, with its sha256 and
  length. The broker checks both before accepting the frame. The test wraps the real
  launcher in a pass-through observer and asserts exactly one render launch. Nothing in the
  measured path is mocked.
- **Fixtures**, both generated by committed code in
  `tests/test_treasurer_slides_lpac_render_spike.py`, with no committed PDF or font bytes:
  - **Subject:** hand-written PDF syntax: one US Letter page of fictional receipt text
    ("Example PTA", invented items and amounts) in the non-embedded `/Helvetica`.
  - **Embedded-font twin:** the same text built at test time through pypdfium2's raw
    text-object calls. It embeds `%WINDIR%\Fonts\arial.ttf`, read at test time.
- **Render settings:** 2,778 permille (200 DPI), so US Letter is exactly 1,700 × 2,200
  pixels. The renderer is pdfium's gray8 bitmap with `FPDF_GRAYSCALE | FPDF_ANNOT`. The
  outside-LPAC anchors use the worker's own render function
  (`_render_native_page_pixels`), called in the test process. The process boundary is
  therefore the only difference between the anchors and the LPAC render.
- **Reference:** the twin, rendered outside the LPAC.
- **Metrics**, each scored against the reference:
  - **Ink coverage.** A pixel is dark when its gray value is below 128. With r = the
    candidate's dark-pixel fraction ÷ the reference's, the score is min(r, 1/r), and 0 when
    r = 0.
  - **Glyph-shape similarity.** The normalized cross-correlation of the two full-page images,
    which is 0 for a constant image.
- **Pinned thresholds** (constants in the test module):
  - `T_INK = 0.75`
  - `T_NCC = 0.80`
- **Calibration.** Every run calibrates in the same test, before the LPAC render is judged.
  The rule is `score(known-good) > T > max(score(all-white), score(box-glyph))` on each
  metric. A metric that fails calibration yields no verdict, and the test fails.
  - **Known-good anchor:** the subject, rendered outside the LPAC.
  - **Known-garbage anchors:** an all-white page, and a box-glyph page that fills every
    tight glyph bounding box of the reference with black (over-inked boxed text).
- **Verdict rule.** The verdict is pass when the LPAC render is above T on both metrics,
  and blocked when it is below T on either. The test asserts that the measured verdict
  equals the one recorded here, and that the blocked findings file exists exactly when the
  verdict is blocked.

## Dev-box readings (2026-10-10)

The host is Windows 11 (build 26200) with Python 3.12, pypdfium2 5.13.0 and PDFium
153.0.7999.0.

| render | ink coverage | glyph NCC | result |
|---|---|---|---|
| known-good: subject outside the LPAC | 0.9991 | 0.9549 | above both thresholds |
| garbage: all-white page | 0.0000 | 0.0000 | below both thresholds |
| garbage: box-glyph page | 0.4357 | 0.6540 | below both thresholds |
| **subject inside the real LPAC** | **0.9991** | **0.9549** | **pass** |

- **Calibration** held on both metrics:
  - ink coverage: 0.9991 > 0.75 > 0.4357
  - glyph NCC: 0.9549 > 0.80 > 0.6540
- **LPAC render:** 1,700 × 2,200 pixels, page count 1. Its raw pixels are byte-identical to
  the outside-LPAC subject render (gray8 sha256 `48d00b9a6d4fa66a…`). The LPAC worker's font
  mapper therefore resolved the same face for `/Helvetica` as an unsandboxed process. The
  render was not a degraded fallback.
- **Wall time:** 9.14 s, 8.47 s, 8.86 s and 9.50 s over four runs. The test measures from just
  before the launch to the validated response, and records the value as
  `lpac_render_spike.lpac_elapsed_s`. Most of the time is worker launch and runtime staging.
  The whole exchange shares the existing 15 s `wall_seconds` ceiling
  (`lpac_render_spike.lpac_wall_seconds_limit`), which leaves at least 5.5 s of margin on
  this host. The test records the elapsed time even when the render fails, so a timeout on a
  slower runner shows its reading.

**Exploratory context (not gated).** These readings came from a scratch probe outside the
committed test, using the same render settings.

- **Built-in fallback face.** When pdfium's system-font lookup was replaced with an empty
  one, pdfium fell back to its built-in face. The subject then scored ink 0.9789 and NCC
  0.9341. A legible substitute face would therefore still clear both thresholds.
- **Hollow 2-pixel outline boxes** ("tofu") scored ink 0.8689 and NCC 0.4471. Ink coverage
  alone would pass tofu; glyph NCC refuses it. That is why the verdict requires both metrics.

## Scope of the render branch

Step 41 added only the three envelope fields the spike needs: `operation` (1 extraction,
2 render; ceiling 2), `render_page_first` (ceiling 25) and `render_scale_permille` (public
value 2,778; ceiling 4,167). Every request carries them, extraction included, and extraction
ignores them. The rendered page is bounded by the existing `max_rendered_pixels_per_page`
and `max_wire_bytes` ceilings. Every worker-side refusal answers the existing
`{"status":"failed"}` frame.

Step 43 completes the protocol:

- the remaining § 5A fields (`render_page_count`, `max_render_raw_bytes_per_page`,
  `max_render_wire_bytes`)
- the render dimension gate
- the `rejected` reasons
- the named `ReceiptRenderError` subclasses
- `render_receipt_pdf`
