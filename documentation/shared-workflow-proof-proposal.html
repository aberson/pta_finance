Example PTA · collaboration proof · publication 1

Two sign-ins.
One shared request.

First prove that two Google users can save and read each other’s comments. Then add an approval decision and a handoff to the second person.

Direction acceptedTechnical review READYNothing implemented yetSteps 32–35 · two separate phases

What I heard

A small workflow that works across accounts.

Start with one requestA fictional classroom-supply request with two items totaling $184.50. Existing private financial records stay in their current workflow.
Make access realTwo independent Google accounts, each recognized by the server. A role switch inside a demo page does not count as sign-in.
Make comments sharedEach person writes a free-text comment; the other reloads and sees the correct author. A new service revision must retain both comments.
Then make a decisionThe reviewer chooses Approve or Not approve using a single-choice checkbox-style control and adds a comment. Approval gives the processor the next action.
Finish the handoffThe processor marks an approved request Complete. That records the administrative workflow; it does not record a payment.

Why this shape

Resolve access and persistence first.

The existing toolkit validates private reimbursement data and renders an offline report. This proof adds a separate Python page/API, Google sign-in protection, and a durable Firestore store. The first page needs only the request, comments, signed-in role, and Reload.

Local tests can prove application behavior. Only the attended cloud test can prove that two real Google accounts reach the intended service and share saved state.

Phase timeline

Two deliveries, with a real check between them.

  1. A

    Shared comments · Steps 32–33

    Step 32 builds the minimal page, verified sign-in boundary, comment transactions, local tests, and safe deployment preparation. Step 33 is the attended M6 test on Cloud Run.

    M6: sign in as A and B → exchange comments → redeploy a fresh revision → read both comments again → verify denial of unauthorized access.

    Start after issue synchronization:
    /build-phase --plan documentation/shared-workflow-proof-plan.md --phase A

    Afterwards: run M6 / Step 33 from the prepared runbook. Phase A’s automatic work ends at Step 32.

M6 is the boundary. Phase B cannot start until the M6 record has been checked and Step 33 is marked DONE. Never run the whole plan as one unattended span: the build runner defers human checks.
  1. B

    Approval handoff · Steps 34–35

    Step 34 adds the reviewer’s decision and processor’s completion action. Step 35 is the attended M7 test using the same two real accounts.

    Approve → processor owns the next action → Complete → no next owner. Not approve → terminal → no next owner. Both people may still comment.

    Only after checked M6 completion:
    /build-phase --plan documentation/shared-workflow-proof-plan.md --phase B

    Afterwards: run M7 / Step 35. Preserve the approved history; use a fresh fictional namespace to test the not-approved branch.

Agent defaults

D1–D10 keep their existing IDs.

These choices stand under the accepted direction. D2, D7, and D8 most affect setup and scope; no repeated approval is needed.

D1

Optional Python service

Add FastAPI/Uvicorn beside the CLI and reuse strict fictional-input validation.

Why: Fits the existing Python/Jinja toolkit without rewriting the private workflow.

Tweak axis: Page wording and layout; a stack replacement needs a new review.

D2

Direct IAP on Cloud Run

Google handles browser sign-in. The server verifies signed assertions and pins two independent subjects to roles.

Why: A small invited-user proof needs a clear access boundary without an application-owned login system.

Tweak axis: Private account assignments and eligible project/OAuth setup; public access is not a fallback.

D3

Separate Firestore state

A keyless runtime identity writes one request and its append-only event history in a dedicated proof namespace.

Why: Container files cannot provide the shared durability this proof needs.

Tweak axis: Private database location and retention; no connection to payment records.

D4

Safe retries; 100-event cap

Version checks prevent stale overwrites. Repeating an operation returns the same receipt. Read the complete bounded history.

Why: Covers multi-user writes without building pagination for two people.

Tweak axis: The event cap if demonstrated use needs it; a new namespace starts another example.

D5

One plain page

Same-origin requests, plain-text comments, explicit reload, and visible save/error feedback.

Why: Makes shared state observable while limiting input and browser security risks.

Tweak axis: Labels and guidance, preserving server authorization and safe text handling.

D6

Explicit private configuration

One JSON environment value supplies project, identity, origin, and store settings. Invalid startup fails clearly.

Why: The app cannot silently load private toolkit settings or fall back to local persistence.

Tweak axis: Private values; verification/error limits remain specified in the plan.

D7

Terminal administrative outcomes

Not approve is terminal. Only the processor completes an approved handoff; completion does not assert money moved.

Why: Proves the two-role flow without inventing payment evidence or a rework product.

Tweak axis: Rework or payment integration would be a separate scoped change.

D8

Small deployment preparation

Stage allowlisted source, run fixed Cloud Build/gcloud commands, inspect the actual image, then deploy its digest.

Why: Prevents private-file upload without building a general cloud reconciliation tool.

Tweak axis: Named resources and conservative service sizing, checked privately in M6.

D9

Separate local and cloud evidence

Local browser/emulator checks precede M6. Separate phase invocations keep M6 before approval implementation; M7 accepts the handoff.

Why: Passing tests does not prove real Google access, cloud permissions, or revision durability.

Tweak axis: Scheduling the attended checks; their order and evidence remain required.

D10

Visible operator prerequisites

Project, billing, permissions, region, two accounts, and IAP OAuth readiness are verified privately.

Why: A plan or successful account login cannot establish cloud readiness.

Tweak axis: Actual operational values and setup owner, without putting them in public files.

Not in v1

The proof ends at the handoff.

Private finance operations

  • No real request import or private bundle edits.
  • No Gmail, Sheets, or Drive integration.
  • No payments, settlement, or sent messages.
  • No reimbursement-policy or parser changes.

Product expansion

  • No request creation, attachments, or rich-text comments.
  • No reopening, reassignment, or multi-organization support.
  • No scheduler, polling, notifications, or dashboard redesign.
  • No generic cloud reconciler or history pagination.

Risks and prerequisites

What still has to be proved.

BoundaryRequired evidence
Google setupUsable project and billing, relevant permissions/APIs, chosen regions, and external-user OAuth/policy compatibility.
Two identitiesTwo distinct verified subjects. Aliases and fake role controls do not satisfy this condition.
Private source safetySource and wheel inspection locally; actual image inspection after Cloud Build, before deployment.
Shared durabilityEach user reads the other’s comment, then both read the same history after a fresh revision.
AuthorizationDirect unauthorized API calls fail: processor cannot decide, reviewer cannot complete, and a declined request cannot complete.
Proof versus adoptionThe demonstration establishes functional behavior. Independent adoption requires separate real-use evidence.
