Why this shape

One useful queue, built on the working handoff.

Keep the original request and its accepted history, then add five packaged fictional requests. Each new request starts awaiting review. Real actions by the two signed-in participants create the varied outcomes visible in the queue.

The list refreshes when opened, when returning from a request, and when Reload is pressed. The first release has no automatic polling. Administrative completion still does not record a payment.

Agent defaults

Concrete choices for the first live version.

These implement the accepted direction. D1, D5 and D7 most affect scope and everyday use. They can be adjusted by ID without repeating approval of the whole plan.

D1

Six fixed requests

What: Enable queue mode with the original request plus five packaged fictional requests.

Why: Enough variety to see the system while keeping setup and verification bounded.

Tweak: Fixture subjects or count before building; real intake needs a later scope.

D2

Keep each history intact

What: Reuse one existing store per request, preserve the original identity and receipts, and seed no decisions.

Why: Existing accepted evidence remains a reliable comparison during the upgrade.

Tweak: New fictional line items; preserving the original history remains required.

D3

Summaries from verified state

What: Read six bounded histories and return their current summaries, ordered by latest activity.

Why: Avoids a second copy of workflow state that could disagree with the detail page.

Tweak: Visible summary labels or ordering; broader scale requires another storage review.

D4

Both roles see the whole queue

What: The same two enabled, verified participants can see all six requests; existing role limits govern actions.

Why: Provides shared transparency without adding team or assignment administration.

Tweak: Per-request visibility would be a separate access-policy change.

D5

Refresh on entry, return and Reload

What: Search and filter the latest loaded list. Returning from details shows all requests and fetches current state.

Why: Makes freshness explicit without a background polling process or saved-filter complexity.

Tweak: Retain filters on return, or consider automatic refresh in a later iteration.

D6

Reuse the authenticated test harness

What: Test real local HTTP, storage and browser behavior, then obtain independent deep code reviews.

Why: Repeatable code checks can exercise failures without exporting Google sessions or weakening production sign-in.

Tweak: Additional realistic scenarios; real hosted acceptance remains separate.

D7

M7 → queue build → M8

What: Finish the existing handoff acceptance, deliver one queue slice, then verify the inspected cloud build with both accounts.

Why: Gives the upgrade an accepted starting point and proves the new deployment preserves it.

Tweak: Browser scheduling and example walkthrough order; each recorded gate still needs its own evidence.

Not in v1

The next milestone has a clear edge.

  • No request import, real reimbursements, uploads or receipt files.
  • No payments, email sending, notifications or Gmail/Drive/Sheets connection.
  • No additional users, organizations, assignment administration or reopening decisions.
  • No arbitrary catalog, pagination, analytics or automatic refresh process.

Risks

What acceptance must establish.

Preservation: The original request and every receipt survive the upgrade and any rollback.

Isolation: A decision, comment, retry or event limit on one request cannot change another.

Freshness: Counts describe the loaded list. Each row is internally consistent; the six reads are not one instantaneous database snapshot.

Actual access: Hosted observations use the two real accounts. Local browser evidence alone cannot establish Google/IAP behavior.

Demonstration size: Six requests show the workflow. They do not establish unrestricted intake or large-scale performance.
